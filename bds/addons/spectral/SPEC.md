# Spectral Player — 実機の仕様（限界値の表）

統合版クライアントが SoundInstance をどう鳴らすかを、**本物のクライアントの録音**から測った値。**実測**と**仮定**（エミュレーター
tools/emu/client.py の既定）を列で分け、実測の出どころ（run の番号・解析）を行ごとに書く。

## 実機と模型: 手元でどこまで再現できるか（11-02、ユーザーの依頼「毎回 Actions で実機テストするのが面倒、完璧に再現できるか」）

**実機の仕組み**（上の表の実測をつなげたもの。どれも redroid の Android 14 と Minecraft 1.26.60.4 で測った）:

1. **サーバー**: アドオンが tick（50 ms）ごとに、聞く人ごとに SoundInstance の命令を送る（1 声 1 回 playSound、あとは setPitch・fade・setVolume。
   0.75 dB より小さい大きさの動き・3 セントより小さい音程の動きは送らない）。1 命令 約 12 B、24 声で 1 tick 平均 28 命令
2. **届いて効く時刻**: 同じ tick の命令は同時に効く（1.4 ms 以内）。tick ごとのばらつき σ 7.3 ms、tick の長さ 49.99–50.17 ms
3. **音の素**: リソースパックの OGG（1760 Hz の正弦波ループ・8 本の帯域ノイズ）。setPitch は再生の速さそのもの（0.12 セント以内）。fade は
   振幅で直線、最短 0.8 ms。setVolume は 2 倍まで指定どおり
4. **同時に鳴る数**: 32。超えると静かなもの（大きさ×音の RMS が小さいもの）・古いものから消える
5. **ゲームのミキサー**: 24 kHz で混ぜる。各音を 24 kHz で直線補間で読む（折り返し止めなし: 12 kHz より上は 24 kHz − f に）。ミックスは
   ファイル単位で約 2.0 で硬くクリップ（リミッターなし）。出力は素材より −32.5 dB・16 bit、2 倍の直線補間で 48 kHz（像は 24 kHz − f）
6. **Android**: ミキサーは 44.1 kHz。録音（AudioPlaybackCapture → scrcpy）は raw 48 kHz 16 bit。メディア音量は録音に効かない
7. **画面と入力**（音とは別の仕組み）: フォームの入力欄は電話では 5000 文字で止まる（リソースパックの 30000 でも）。その実行の最初の
   フォームの送信は返事が来ない。adb の input text は英数字だけ（約 200–330 文字/秒）

**模型**（tools/emu/client.py ＋ tools/emu/spec.json ＋ tools/exp/exp.py の path24。変換ページの「聞く端末: 電話」も同じ測った値の
JavaScript 版 web/game.js）は 1–6 をそのまま持つ: アドオンの本物の bundle を録る用のモックで動かして命令を取り（tools/sim/run_song.mjs）、
その命令を測った規則で鳴らし、測った経路を通す。

**どこまで合うか**（tools/rig/emu_validate.py、33 回目の 26 本の録音: 13 曲 × 2 通りのデータ。measured/emu-validation-2026-11-02.json。
模型は**推測**、録音は**実測**）:

| 物差し | 結果 | 読み方 |
|---|---|---|
| 成績の予測（模型の ViSQOL − 実機の ViSQOL） | **平均 +0.055・絶対値の平均 0.074・相関 0.958**。26 本中 19 本が ±0.07 以内、22 本が ±0.10 以内 | 外れはドラム（+0.47 / +0.36）と英語の朗読（+0.13 / +0.17）: 模型が甘い |
| 音そのものの近さ（模型の音を録音と並べた ViSQOL、録音が基準） | **中央値 4.33**（3.93–4.66）。ピアノ・話し声・オーケストラは 4.46–4.66、EDM・ロックは 3.93–3.99 | 最初の模型は 1.4–2.7 だった（「実測から分かったこと」の 4.） |
| 1/3 オクターブの差（模型 − 録音） | 50 Hz–5 kHz は ±0.15 dB、6–12 kHz で −0.1〜−0.44 dB | 高い所を模型が少し小さく出す |
| A/B の差（z − o: SPZ2 にした曲と元の曲） | 模型 +0.003・実機 +0.002（どちらも差なし）。向きの一致 10/13（両方 0.02 以内を含む） | 本当の差が無い組なので曲ごとの相関は出ない（−0.02）。差が大きい組での確かめは 12 回目の +6/+8/+10 dB |

比べる相手として、**実機は実機自身とも完全には合わない**: 同じ run の中で同じ曲を 2 回録ると ±0.05 ほど、run をまたぐと同じデータでも
曲ごとに平均 0.27 動く（tick ごとの着地のばらつき σ 7.3 ms・録音の抜け）。模型の外れ（絶対値の平均 0.074）は run の中のゆらぎと同じくらい。

**手元で済むこと / 実機が要ること**:
- 手元で済む（模型で決めてよい）: 変換器・曲テキストの格子・合成による分析の設定・声の数・レベル・ライブの変換器の変更。これまでの
  決め方（模型で選んで、実機は最後に 1 回）で、+10 dB と +6 dB の差の向きは 13 曲中 12 曲で実機と同じだった（11 回目）
- 実機が要る: ①画面と入力（フォーム・入力欄の上限・キーボードや入力メソッド・最初の送信の取りこぼし。35 回目の漢字も）
  ②模型に無い鳴らし方（新しい音の素・3D の距離や向きの新しい使い方）③ゲームの更新の後（upkeep の後に較正の 1 回: calib）
  ④ドラムの立ち上がり（模型がいちばん甘い）
- 使い方: `python3 tools/emu/phone.py <曲.song.json> --corpus <曲> --wav out.wav`（電話が録るはずの音と、リグと同じ物差しの成績、1 分ほど）。
  変換ページの「▶ ゲーム内の音」＋「聞く端末: 電話」も同じ模型。実機を回したら `python3 tools/rig/emu_validate.py --run <id>` で模型がずれていないか

## 曲の成績（実測: 実機の録音の ViSQOL v3）

### 35 回目（run 41398498360: 漢字の曲テキストを入力メソッドで — 1 文字も届かなかった。5 回目のセッション）

1 部だけの曲テキストを 4 つ: 漢字（SPZ2）1593・4994・5984 文字は入力メソッド ADBKeyBoard（app/lib/unitext.mjs: 入力欄を開いて
タップした**後に**切り替えて放送で送り、終わったら戻す）、英数字（SPA2）4977 文字は adb のキーで。実測:

- **英数字 4977 文字は 1 回で貼れた**（ck_ok_a50）→ 5000 文字までのパートは電話で通る（34 回目の 5000 ちょうどと合う）
- **漢字は 3 つとも断られ、届いたのは 1000 文字未満**（ck_n_under1000・ck_refused_any。「切れた」でも「曲のテキストでない文字」でもない
  = 空: 打った漢字がゲームの入力欄に入っていない）。入力欄の下で入力メソッドを切り替えると、ゲームの欄はその入力を受け取らない（推測:
  切り替えでキーボードが閉じ、欄の編集が終わる）。漢字が文字で数えられるかは分からないまま
- → リグに `ime on` / `ime off`（欄を開く**前**に切り替えたままにする: app/README.md）。36 回目で、英数字 1593 文字も同じ道で送って
  道そのものを確かめ、漢字 1593・4994・5984 文字をもう一度

### 34 回目（run 41393759902: **電話の入力欄は 5000 文字ちょうどで止まる**。5 回目のセッション）

小さな SPA2 を 2 回（最初の 1 回の取りこぼし避け: 2 回目に返事あり）の後、15142 文字の SPA2 を 200 文字ずつ打って送り、断られた貼り付けの
文字数を桁ごとの ck（thousands_*・hundreds_*・tens_*・units_*）で読んだ。実測: ck_thousands_5・ck_hundreds_0・ck_tens_0・ck_units_0・ck_cut_short
= **届いたのは 5000 文字ちょうど**（15142 のうち。サーバーの理由は「the text is cut short」）。リソースパックの 30000 でも、バニラの 100 でもない、
電話のクライアント側の上限（プロトコルのクライアントからは 29028 文字の漢字も BDS に届く）。打ったのは英数字（adb の input text が打てるのは
ASCII だけ）。→ **パートは 5000 文字まで**（src/songtext.ts の FIELD_CHARS: 変換ページ・tools/songtext.mjs・アドオンの案内）。5000 文字で
切れた曲のテキストには「電話の入力欄は 5000 文字まで: 変換ページで作り直して 1 つずつ」とアドオンが言う（tests.txt）。漢字（SPZ2）が文字で
数えられるか UTF-8 のバイト（1 文字 3 バイト → 1666 文字）で数えられるかはまだ分からない: 35 回目で、入力メソッド（app/lib/unitext.mjs）で
漢字を 1593・4994・5984 文字入れて確かめる（Bedrock のコマンドブロックは日本語だと上限 500 の 3 分の 1 の 167 文字で止まる、という報告がある:

## 実測から分かったこと（設計に効くもの）

1. **同時発音数 32**: quality の 56 本（48 声＋ノイズ 8）と打撃音は上限を超え、静かな声が tick ごとに消えたり戻ったりする。24 声
   （＋ノイズ 8 = 32）は並べて録った 4 曲で 48 声より上（+0.17〜+0.52）、13 曲では中央値が同じ（1.99）で命令が 3 分の 1 少ない →
   **電話（platformType Mobile）は既定 24 声**（src/main.ts の CLIENT_SOUNDS。測っていない端末は今までどおり）。軽量（16 声・打撃音
   なし）は中央値 2.15 で一番高いが、立ち上がりの合致率が 0.26 に落ちる（打撃音が無い）。
2. **ワンショットは命令より 1 tick 遅い**: 打撃音が声より約 49 ms 遅れ、立ち上がりの合致率が低かった（ドラム 0.08）→ **打撃音を
   1 tick 先に送る**: 実機でドラム 0.08 → 0.63・ファンク 0.54 → 0.77、13 曲の中央値 0.47 → 0.52、ViSQOL の中央値 1.99 → 2.05。
3. **変換器の癖**（エミュレーターでも同じ）: 13 曲の中央値で 28 Hz −6.2 dB・18 kHz −3.3 dB、曲によって 1–3 kHz が +5〜+17 dB
   （ドラム・ロック・EDM・ファンク）、最低域が −11〜−17 dB（ロック・ファンク・話し声）。measured/converter-band-bias-emulated.json。
4. **エミュレーターと実録音は（最初は）合っていなかった**: 実測の spec を入れても ViSQOL 1.4–2.7（基準 4.5 に届かない）。録る経路
   （ゲームの 24 kHz のミックス・−32.5 dB・16 bit・2 倍の直線補間）を入れた後は、曲の成績を相関 0.87–0.97 で当てる
   （measured/emu-validation-2026-10-31.json）。打撃音なしの版では、エミュレーターが実機より 0.0–0.38 高い（平均 0.17）。
5. **天井を下げているのは量子化**（静かな曲）: ゲームはどの音もファイルより 32.5 dB 小さく 16 bit で鳴らす。経路の模型で元の曲を
   12 dB 大きく通すと 10 曲の天井の中央値 3.11 → 3.90（推測）。曲データの側も同じで、**ファイルより大きく鳴らす**（setVolume を 1 より
   上に）と静かな曲ほど上がる。ミックスはファイル単位で約 2.0 でクリップするので（calib loud、実測）、電話の既定は +6 dB。
6. **打撃音（ワンショット）は無い方がよい**（5 回目、同じ run の 13 曲）: 変換器 residual voiced で打撃音を鳴らさない改良版が出荷版より
   中央値 +0.34（1.95 → 2.29）、13 曲中 11 曲で上。打撃音を 1 tick 後ろにずらしても（4 曲中 3 曲で下）、命令を 24/tick に絞っても
   （4 曲中 3 曲で下）よくならない。最終の変換は打撃音を作らず（そのエネルギーはノイズ帯域に残る）、立ち上がりはノイズ帯域の
   tick ごとのフェード（5–50 ms）で作る。
7. **曲パックの最初の script event**: /scriptevent は 2048 文字まで。meta に tick ごとのフェードの符号（base64）を入れると最初の部分に
   入りきらない（6 回目が落ちた）→ 形式 2 は符号を曲データの後ろに置き、meta には長さだけ。
