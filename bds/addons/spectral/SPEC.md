# Spectral Player — 実機の仕様（限界値の表）

統合版クライアントが SoundInstance をどう鳴らすかを、**本物のクライアントの録音**から測った値。**実測**と**仮定**（エミュレーター
tools/emu/client.py の既定）を列で分け、実測の出どころ（run の番号・解析）を行ごとに書く。

## 測った端末と録り方

| | |
|---|---|
| クライアント | redroid（コンテナの Android 14 x86_64、MindTheGapps）に Play が入れた **Minecraft 1.26.60.4**（改造なし）。platformType は Mobile |
| サーバー | GitHub Actions のランナー上の BDS 1.26.60.6（1.26.60.4 の配布なし）＋ Spectral Player、LAN で参加 |
| 録音 | scrcpy 3.1 `--audio-source=output`（AudioPlaybackCapture）、raw 48 kHz 16 bit ステレオ。Android のミキサーは 44.1 kHz |
| 操作 | redroid では lab-pad の uinput コントローラーが Android の入力の一覧に出ない（/dev/input にノードを作っても）ので、シェルの長押し入力（app/lib/android.mjs の startPad） |
| 音量 | `audio volume`: Android のメディア音量 15/15、ゲームの audio_main 1・audio_music 0（BGM が録音に入らないように）。準備した端末の既定は 5/15・0.5・0.3（measured/device-audio-41065460620.json） |
| 数の出し方 | app.txt の `audio analyze`（tools/rig/analyze.py・score_song.py・emu_check.py）がジョブのログに `[spectral rig]` の行で出す。録音そのものは `audio export`（Opus にして実行の成果物の public/spectral/rec/ に平文で: 管理パネルでサインインして聞ける・notify.yml が Discord に送る・tools/rig/fetch_rec.py で取る。8 回目までは暗号化してログへ） |
| 集めたもの | measured/redroid-<run>.json（tools/rig/collect.py）、measured/summary.json（tools/rig/summary.py）、measured/calib-*.json、measured/device-audio-*.json、measured/traffic-*.json |

## 限界値（端末: 上の redroid の Android 14・Minecraft 1.26.60.4）

- **音域別の元素材**: 高い音の雑音成分は出る周波数だけで決まり（素材と倍率によらない）、録る経路のもの。素材を分けても変わらない
- **ノイズを 24 Bark 帯域に**: 24 本で同時発音数 32 のほとんどを使い、正弦波が 8 本しか残らない
- **ステレオ化**: 左右を独立に鳴らせる（67 dB）が、左右で本数が倍になり 32 本に入らない
- **原子バンク**: ワンショットは 1 tick 遅れ（49 ms、σ 7 ms）で、細かい粒は置けない。打撃音の 4 段の先頭無音（12.5 ms 刻み）で十分な精度
- **ビブラート・グライドのループ、微分できるエミュレーターでの最適化**: エミュレーターが実録音と合っていない（ViSQOL 1.4–2.7）ので、
  その上での最適化は実機の改善を保証しない。先に模型を合わせる（録る経路の雑音・声の出入り）

## 実測から分かったこと（設計に効くもの）

1. **同時発音数 32**: quality の 56 本（48 声＋ノイズ 8）と打撃音は上限を超え、静かな声が tick ごとに消えたり戻ったりする。24 声
   （＋ノイズ 8 = 32）は並べて録った 4 曲で 48 声より上（+0.17〜+0.52）、13 曲では中央値が同じ（1.99）で命令が 3 分の 1 少ない →
   **電話（platformType Mobile）は既定 24 声**（src/main.ts の CLIENT_SOUNDS。測っていない端末は今までどおり）。軽量（16 声・打撃音
   なし）は中央値 2.15 で一番高いが、立ち上がりの合致率が 0.26 に落ちる（打撃音が無い）。
2. **ワンショットは命令より 1 tick 遅い**: 打撃音が声より約 49 ms 遅れ、立ち上がりの合致率が低かった（ドラム 0.08）→ **打撃音を
   1 tick 先に送る**: 実機でドラム 0.08 → 0.63・ファンク 0.54 → 0.77、13 曲の中央値 0.47 → 0.52、ViSQOL の中央値 1.99 → 2.05。
3. **変換器の癖**（エミュレーターでも同じ）: 13 曲の中央値で 28 Hz −6.2 dB・18 kHz −3.3 dB、曲によって 1–3 kHz が +5〜+17 dB
   （ドラム・ロック・EDM・ファンク）、最低域が −11〜−17 dB（ロック・ファンク・話し声）。measured/converter-band-bias-emulated.json。
4. **エミュレーターと実録音は（最初は）合っていなかった**: 実測の spec を入れても ViSQOL 1.4–2.7（基準 4.5 に届かない）。録る経路
   （ゲームの 24 kHz のミックス・−32.5 dB・16 bit・2 倍の直線補間）を入れた後は、曲の成績を相関 0.87–0.97 で当てる
   （measured/emu-validation-2026-10-31.json）。打撃音なしの版では、エミュレーターが実機より 0.0–0.38 高い（平均 0.17）。
5. **天井を下げているのは量子化**（静かな曲）: ゲームはどの音もファイルより 32.5 dB 小さく 16 bit で鳴らす。経路の模型で元の曲を
   12 dB 大きく通すと 10 曲の天井の中央値 3.11 → 3.90（推測）。曲データの側も同じで、**ファイルより大きく鳴らす**（setVolume を 1 より
   上に）と静かな曲ほど上がる。ミックスはファイル単位で約 2.0 でクリップするので（calib loud、実測）、電話の既定は +6 dB。
6. **打撃音（ワンショット）は無い方がよい**（5 回目、同じ run の 13 曲）: 変換器 residual voiced で打撃音を鳴らさない改良版が出荷版より
   中央値 +0.34（1.95 → 2.29）、13 曲中 11 曲で上。打撃音を 1 tick 後ろにずらしても（4 曲中 3 曲で下）、命令を 24/tick に絞っても
   （4 曲中 3 曲で下）よくならない。最終の変換は打撃音を作らず（そのエネルギーはノイズ帯域に残る）、立ち上がりはノイズ帯域の
   tick ごとのフェード（5–50 ms）で作る。
7. **曲パックの最初の script event**: /scriptevent は 2048 文字まで。meta に tick ごとのフェードの符号（base64）を入れると最初の部分に
   入りきらない（6 回目が落ちた）→ 形式 2 は符号を曲データの後ろに置き、meta には長さだけ。
